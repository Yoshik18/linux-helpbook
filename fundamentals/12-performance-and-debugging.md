# 12. Choose the next debugging command

Record the failing operation, time and affected client/process first. The goal
is a useful next observation, not running every tool on the host.

## Use symptoms to choose a starting point

| Symptom | Start with | Look for |
|---|---|---|
| Host feels slow | `uptime`, `vmstat 1 5`, `top` | Runnable work, blocked work, repeated CPU activity |
| One process grows | `ps`, selected `/proc/PID/status` fields | RSS/threads over time, workload changes |
| Writes fail | `df -h`, `df -i`, `du -x` | Capacity, inode exhaustion, directory ownership |
| HTTP request fails | `getent`, `ss`, `curl -v` | Resolution, listener address, connection/TLS/HTTP stage |
| Service fails to start | `systemctl status`, filtered `journalctl` | Exit cause, config errors, dependencies |

The table chooses a direction, not a diagnosis. High utilization can mean useful
work; waiting and errors need context. Compare the same scope and time window.

## Look at per-process activity when system totals hide the issue

```bash
ps -p "$$" -o pid,ppid,stat,pcpu,rss,nlwp,comm
awk '/^(Threads|voluntary_ctxt_switches|nonvoluntary_ctxt_switches):/ {print}' "/proc/$$/status"
```

`NLWP` is the thread count in procps ps. Context-switch counters are cumulative;
a large lifetime value does not prove this minute is unhealthy. A one-thread
hotspot, CPU quota or lock can affect an application while host CPU looks idle.

If sysstat tools are installed, these are bounded inspection recipes:

```bash
pidstat -p "$$" 1 3
iostat -xz 1 3
```

`pidstat` samples one process. `iostat -x` adds device detail and `-z` omits
inactive devices. Compare interval latency/queues and throughput, not `%util`
as a universal storage-capacity score. First-report semantics and available
fields vary with tool versions. No workload is generated by these queries.

## Inspect files and sockets for a specific process

```bash
ls -l "/proc/$$/fd"
readlink "/proc/$$/cwd"
```

With lsof installed, `lsof -p PID` can describe that process's open resources.
Replace PID only with a process you are allowed to inspect. Descriptor paths
and arguments can be private. A large descriptor count is a clue to compare
with limits and workload, not automatic proof of a leak.

## Trace a tiny command you own

Only if strace is already installed and the environment allows child tracing:

```bash
strace -e trace=write printf 'trace practice\n'
```

Strace launches an external `printf` here and reports selected system calls,
normally including a write to stdout. It does not reveal every application
function or explain CPU time spent without syscalls. Filters reduce output,
not all overhead or disclosure risk. Do not attach to a live service or relax
ptrace/seccomp restrictions to finish a lesson.

For profiling, `perf stat -- sleep 1` is a small example of measuring an owned
command, not a promised portable check. Permissions, event access and container
restrictions may block it. No perf or strace execution is claimed here.

## Compare evidence before changing configuration

```bash
vmstat 1 3
```

Record the interval and affected workload. If CPU is suspected, compare runnable
work with actual allowed capacity. If I/O is suspected, correlate waiting with
device and application latency. If memory is suspected, compare available memory,
reclaim/swap activity and container events. A restart can erase the evidence.
Do not tune a kernel setting merely because a counter is nonzero.

## Practice

A request times out, but CPU is mostly idle. Choose three checks that separate
network reachability, a missing listener and application waiting. State what
each observation would and would not establish.

<summary>One possible sequence</summary>

Use a permitted name-service lookup, inspect the server's expected listening
